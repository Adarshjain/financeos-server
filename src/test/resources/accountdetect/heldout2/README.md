# Held-out account-detection corpus v2 (heldout2)
Second, broader independent corpus; same author rules as heldout/ (engine code in gmail/ never read). Schema = v1 plus two expected-account fields.
- dev/ (20 mailboxes) visible to the engine developer; sealed/ (20 different mailboxes): only pass/fail counts are reported.
- One JSON per mailbox: {mailbox, today, mails[{id, from, subject, body, date, attachments[{filename, protected, pdfText?}]}], expected{accounts[], mustNotReport[]}}.
- expected.accounts fields as in v1 (issuerDomain, last4, kind, variant, lifecycle, lifecyclePartnerLast4, minEvidence) plus limitBucket and addonOf.
- limitBucket: <1L, 1-3L, 3-5L, 5-10L, >10L from the LATEST total credit limit stated in any statement or limit-change mail; null if never stated (accounts, debit cards, add-ons, charge cards, cards with only protected statements).
- addonOf: primary card last4 for ADDON accounts, else null (lifecyclePartnerLast4 equals it for ADDON).
- variant = product's short marketed name without issuer words or "Credit Card" (newest name after a rename/upgrade); generic tier words alone, plain savings/current/debit and OneCard are null. v1 labels were re-labelled by the same rule (7 edits).
- Mails 86 to 400 per mailbox over 6 to 36 months; 3 to 8 unlocked statements (pdfText, line-oriented per-issuer layouts; MITC PDFs are noise) plus many protected ones.
- 40 issuers incl. PSU, small finance, payments banks, fintech cards. Ex-Citi to Axis migration dates are compressed into the 36-month window (fictional timing).
- Traps: all v1 traps plus ex-Citi to Axis new number, renamed product, co-brand name equal to a merchant used on other cards, add-on only in primary statement, combined two-card statement, closure only in statement, limit increase, card number only in statement, SFB savings+current, payments-bank wallet (in mustNotReport, never a card).
- All names, amounts and numbers are made up; bank names, domains and product names are real. Generated by a seeded script (reproducible).
